# Дополнительные методы публичного API

Кастомные методы KAPI, построенные на публичном REST API KUMA. В примерах `client`, `source` и `target` — экземпляры `RestClient`.

## Постраничный поиск алертов

```python
for alert in client.alerts.iter_search(status=["new"]):
    process(alert)

status, alerts = client.alerts.searchp(limit=500, status=["assigned"])
```

`iter_search()` выдаёт алерты по одному, `searchp()` собирает до `limit` записей в список. Повторная страница вызывает `APIError`.

## Поиск по содержимому ресурсов

```python
status, result = client.resources.find_content(
    kind="filter",
    tenant_ids=[tenant_id],
    query="powershell",
)
```

Совпадения — в `result["rows"]`, полнота поиска — в `result["complete"]`. Если `result["state"]` не `None`, передайте его как `state=` в следующий вызов с теми же условиями.

## Словарь в активный список

```python
status, response = client.dictionaries.to_active_list(
    dictionary_id="dictionary-id",
    correlator_id="correlator-service-id",
    active_list_id="active-list-id",
    dictionary_key="hostname",
    clear=False,
)
assert status == 204
```

`dictionary_key` должен существовать в CSV. Пустые и повторяющиеся ключи отклоняются до отправки импорта. Выбранная колонка становится `key`; прежняя `key` получает имя выбранной колонки. Остальные столбцы, включая `value`, сохраняются. `clear=False` не передаёт серверу флаг очистки.

## Активный список в словарь

```python
status, report = client.active_lists.to_dictionary(
    correlator_id, active_list_id, dictionary_id,
    on_conflict="update",  # keep по умолчанию; update заменяет строку целиком.
    columns={"value": "login"},  # Столбец словаря → поле AL.
    invalid_rows="skip",   # Пропускать некорректные записи AL.
    clean_existing=True,   # Удалять некорректные строки и дубли словаря.
    return_report=True,    # Вернуть счётчики и исходный ответ сервера.
    dry_run=True,          # Только план; False — применить изменения.
    timeout=(5, 120),      # connect/read для каждого запроса.
)
print(report["added"], report["replaced"], report["skipped"], report["dropped"])
```

- `active_list_key="key"` — ключ AL; можно указать поле из `record`.
- `columns` переименовывает выбранные поля; остальные читаются по имени, отсутствующие дают пустую строку. При повторах ключа в AL берётся первая корректная запись.
- По умолчанию ошибка строки останавливает запись; `max_cell_len=1024` — лимит ячейки.
- `clear=True` заменяет всё содержимое; полная очистка построчная и не атомарна. `dry_run=True` всегда возвращает отчёт: `would_update` показывает наличие изменений, `updated=False`.
- Без `dry_run` и `return_report` результат — `(status, response)`. Все параметры — в docstring метода.

## Связи правил и корреляторов: публичный API

```python
status, correlators = client.resources.get_bound_correlators(rule_id, tenant_ids=[tenant_id])

# Для множества правил — один обход, без повторного чтения каждого коррелятора.
for binding in client.resources.iter_rule_bindings(rule_ids=rule_ids):
    process(binding)
```

`get_bound_correlators()` возвращает `(200, [{id, name, tenantID}, ...])`. `iter_rule_bindings()` выдаёт `{ruleID, correlatorID, correlatorName, tenantID}`. `tenant_ids` ограничивает тенанты корреляторов; правила Shared могут использоваться в другом тенанте. `None` означает все доступные тенанты, пустой список отклоняется. Учитываются конфигурации, включая корреляторы без запущенного сервиса; результат ограничен правами токена.

Реализация использует документированные публичные методы `GET resources` и `GET resources/correlator/{id}`. Отдельный публичный маршрут `bound_to_list` на стендах не подтверждён. Один обход читает каждый коррелятор один раз; вызов `get_bound_correlators()` для каждого правила повторял бы обход, поэтому для массовой обработки используйте итератор.

`resources.iter_search(**filters)`, `resources.iter_correlators(tenant_ids=None)` и `services.iter_search(**filters)` читают страницы до пустой. Короткая страница не завершает обход; повтор страницы вызывает `APIError`. Коллекции не являются атомарным снимком: одновременные изменения в KUMA могут влиять на результат.

## CSV-отчёт по правилам: только публичный API

```python
status, result = client.resources.export_rules_csv(
    "correlation_rules.csv",
    tenant_ids=None,
    include_shared=True,
    name_contains="#",
    strip_tenant_prefix=True,
    delimiter=",",
)
# result: path, rules — число ресурсов, rows — число групп, bindings — число связей.
```

Колонки: `Название`, `Количество тенантов`, `Тенанты`, `Корреляторы`. `Количество тенантов` — число уникальных ID тенантов, в которых существуют правила группы. Дубли одного правила в конфигурации коррелятора исключаются; непривязанные правила также попадают в отчёт. Имена тенантов берутся из публичного метода `tenants`, в том числе если KUMA 4.2 возвращает пустой `tenantName` для Shared.

По умолчанию выбираются имена с `#`; `name_contains=""` включает все правила. Фильтр трактуется как буквальная подстрока на обеих версиях KUMA. `strip_tenant_prefix=True` удаляет часть имени до первого `#` включительно, как в исходном отчёте; для группировки по полному имени передайте `False`. Это явное преобразование имени, а не распознавание тенанта. `tenant_ids` фильтрует владельцев правил; привязки ищутся во всех доступных корреляторах, чтобы сохранить межтенантные связи с Shared.

Метаданные загружаются постранично, каждый коррелятор читается один раз. Индекс правил и связей хранится во временной SQLite-базе с кешем 8 МиБ. В памяти остаются текущая страница, одна конфигурация коррелятора, одна группа CSV и отпечатки страниц; все правила и связи в общий список не собираются. Размер одного полного коррелятора определяется ответом KUMA. Пустая выборка правил не запускает обход корреляторов.

CSV записывается построчно в UTF-8 с BOM; кавычки, разделители и переносы внутри значений экранируются модулем `csv`. Группы сортируются по имени. Целевой файл заменяется атомарно после успешного завершения; при ошибке прежний файл сохраняется, временные файлы удаляются. Нужны права публичного API на чтение тенантов, поиск ресурсов и чтение конфигураций корреляторов. Приватный клиент не используется.

## Массовая привязка и перезагрузка: публичный API

```python
for result in client.resources.iter_update_correlators(
    correlator_ids, rule_ids, action="link", reload=False,
):
    process(result)

status, services = client.services.reload_resource(correlator_id)
```

`action` — `link` или `unlink`. Указываются ID ресурсов корреляторов, не ID сервисов. Результат итератора содержит `correlatorID`, `status`, `services`; правила и корреляторы в аргументах дедуплицируются. По умолчанию меняются только конфигурации. `reload=True` явно включает перезагрузку связанных сервисов через публичный API; `reload_resource()` сопоставляет `service.resourceID`, затем передаёт `service.id` в `services.reload()`. Если сервисов нет, возвращается `(200, [])`.

Итератор останавливается при первой ошибке; ранее выполненные изменения остаются. Чтение и последующая запись конфигурации не атомарны относительно других авторов. Обход нескольких инсталляций выполняется приложением отдельными `RestClient`; библиотека не хранит список адресов и учётных данных.

## Синхронизация с эталоном: публичный API

```python
_, rule_template = source.resources.get("correlationRule", template_rule_id)
status, result = target.resources.sync_correlation_rule(
    target_rule_id, rule_template, preserve_custom=True,
)

_, correlator_template = source.resources.get("correlator", template_correlator_id)
status, result = target.resources.copy_correlator_variables(
    target_correlator_id, correlator_template,
)
```

Синхронизация правила переносит имя, `identicalFields`, `uniqueFields`, `rateLimit`, `keepPolicy`, `uniqueFieldsMapping`, переменные соответствующих селекторов и поля `output`, `loop`, `noAlert`, `enrichment` совпадающих действий. ID, тенант, условия селекторов и остальные поля цели сохраняются. Количество селекторов должно совпадать. При `preserve_custom=True` сохраняются переменные цели с `custom` в имени без учёта регистра; при совпадении имени они имеют приоритет над эталоном. Ссылки внутри эталона должны быть доступны на целевой KUMA: автоматического переназначения ID здесь нет.

`copy_correlator_variables()` заменяет только `payload.variables`. Входные объекты не изменяются; при отсутствии изменений PUT не отправляется. Оба метода возвращают `(status, resource/response)` и не перезагружают сервисы.

## Пакетный перенос ресурсов: публичный API

```python
for result in source.resources.iter_copy_to(
    target,
    resource_ids,
    source_tenant_id,
    target_tenant_id,
    password=archive_password,
    on_conflict="preserve",
    backup_directory="backups",
    batch_size=100,
    chunk_size=1024 * 1024,
    timeout=(5, 120),
):
    process(result)
```

`target` — экземпляр `RestClient` с явно выбранной версией целевой KUMA; `source` также является клиентом. Перенос выполняется по этапам: экспорт → потоковое скачивание во временный файл → загрузка → чтение оглавления → импорт. Одновременно обрабатывается не более `batch_size` исходных ID; зависимости и TOC архива могут быть больше. Архивы не собираются в памяти. `timeout` переопределяет экспорт, скачивание и загрузку; TOC и импорт используют таймаут клиента. Совместимость формата архива между разными версиями определяет KUMA; тестирование каждой версии отдельно не гарантирует любой перенос между версиями.

| `on_conflict` | Поведение при HTTP 409 |
| --- | --- |
| `error` | Значение по умолчанию: вернуть ошибку без автоматической замены. |
| `replace` | Сохранить резервные архивы конфликтующих ресурсов и повторить импорт с действием `2` для конфликтующих кандидатов. |
| `preserve` | После того же повторного импорта восстановить конфликтующие ресурсы из резервных архивов, сохранив локальные настройки. Восстановление выполняется и при ошибке повторного импорта. |

Для `replace` и `preserve` нужен существующий `backup_directory`; пароль архива передаётся явно и не записывается библиотекой на диск. Конфликты разбираются из `APIError.details` как объект или JSON-строка, включая формат 4.2. Ресурсы разных исходных тенантов резервируются и восстанавливаются раздельно. При восстановлении заменяются только конфликтовавшие ресурсы; остальные зависимости из резервного архива не запрашиваются на замену.

Результат пакета содержит `status`, `resourceIDs`, `result`, `backups`, `backup_path` и `conflicts_restored`. `backups` перечисляет путь, исходный тенант и ID каждого резервного набора; `backup_path` — первый путь для удобства. Резервные архивы остаются на диске. При ошибке после резервирования и начала повторного импорта `APIError` содержит `backups`, `backup_path`, `conflicts_restored`; исходная ошибка доступна через `__cause__`.

Перенос не является транзакцией: предыдущие пакеты и часть текущего импорта могут сохраниться после ошибки. Совпадение имён не гарантирует конфликт: при переносе между тенантами KUMA может создать копию с изменённым именем. Метод переносит содержимое ресурсного архива по контракту KUMA, а не произвольное состояние запущенных сервисов или данные активных списков. Автоматической перезагрузки нет.
